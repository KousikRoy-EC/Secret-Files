This is an excellent project for a resume because it touches on several advanced system programming concepts: process management, signals, inter-process communication (IPC), concurrency, and memory management. 

To help you understand your `qsched` project inside and out for your interview, let's break down exactly how it works, step-by-step.

### 1. The Core Flow: The Main Loop
At the heart of your `qsched` daemon is an infinite loop (usually a `while(1)` or `while(daemon_running)` loop). This is the "scheduler." 

**How it works:**
1. **Sleep and Wake:** The loop uses a system call like `sleep(1)` so it wakes up exactly once every second.
2. **Check Time:** When it wakes up, it gets the current system time using functions like `time()` and `localtime()`. This gives it the current minute, hour, day of the month, month, and day of the week.
3. **Scan Tasks:** It then iterates over an in-memory list (like an array or linked list) of all the scheduled tasks that were loaded from your configuration file.
4. **Match and Execute:** For every task, it checks: *"Does the current time match the task's schedule?"* It does this by evaluating the cron syntax (handling exact numbers, wildcards `*`, and steps `*/5`). If the time matches, it triggers the execution of that task.

### 2. How Tasks Get Executed: `fork()` and `exec()`
When the scheduler finds a task that needs to run right now, it **does not** run the command itself directly in the main program. If it did, a long-running script would pause the entire scheduler, and no other tasks would run until it finished!

Instead, it uses the classic UNIX **fork-exec** pattern:

1. **`fork()`**: The parent daemon calls `fork()`. This system call clones the current process, creating a "Child" process. The Child is an exact duplicate of the Parent at that exact moment.
2. **The Split:** 
   - **In the Parent:** `fork()` returns the Process ID (PID) of the new Child. The Parent instantly moves on, continuing its loop to check other tasks. It does not wait for the Child.
   - **In the Child:** `fork()` returns `0`. The Child knows it is the worker. It immediately calls an `exec` family function (like `execl("/bin/sh", ...)`).
3. **`exec()`**: This function replaces the Child's current memory and program with the shell (`/bin/sh`) and tells it to run your specific command.

**Why this is crucial:** Isolation. If the scheduled script crashes, has a memory leak, or gets stuck in an infinite loop, only the isolated Child process is affected. The Parent daemon keeps ticking away safely.

### 3. Handling Multiple Tasks at the Same Time
What happens if you have three different scripts all scheduled to run at exactly `12:00 PM`?

1. At 12:00:00, the daemon wakes up and scans the list.
2. It sees Task A matches. It calls `fork()`. Child 1 is created. The Parent instantly continues.
3. It sees Task B matches. It calls `fork()`. Child 2 is created. The Parent instantly continues.
4. It sees Task C matches. It calls `fork()`. Child 3 is created. The Parent finishes scanning the list.

**The result:** You now have the main daemon and three child processes running simultaneously. The Operating System's CPU scheduler takes over and runs Child 1, Child 2, and Child 3 in parallel. The daemon itself never blocked; it just rapidly dispatched the jobs and went back to sleep until 12:00:01.

### 4. Preventing "Zombie" Processes (Signal Handling)
When a child process finishes running its script and exits, it doesn't completely disappear. It becomes a **"Zombie"**. It leaves behind a tiny data structure in the OS so the Parent can eventually read its exit status (success or failure). 

If a cron daemon runs forever and spawns thousands of tasks, but never cleans up these zombies, the system will run out of available Process IDs (PID exhaustion), and the whole server will crash.

**How you solved this:**
You set up a **Signal Handler** for `SIGCHLD`. When a child dies, the OS automatically sends the `SIGCHLD` signal to the Parent.
1. The Parent's normal loop is momentarily interrupted, and the signal handler function executes.
2. Inside the handler, you call `waitpid(-1, NULL, WNOHANG)`.
3. **The Magic of `WNOHANG`:** Normally, `waitpid` pauses the program until a child finishes. `WNOHANG` tells it: *"Clean up any dead children right now, but if no children are dead, do not wait, return immediately."* 
4. You usually put this in a `while` loop inside the handler to clean up multiple children if several died at the exact same millisecond. 

### 5. Handling Race Conditions and Thread Safety
Even though you are using multi-processing (`fork`) to run tasks, the daemon itself is multi-threaded. Why? Because of configuration reloads.

Imagine the daemon is in the middle of scanning its task list to see what to run. Suddenly, the system administrator updates the config file and sends a `SIGHUP` signal to the daemon, telling it to reload the new configurations without restarting.

**The Race Condition:**
If the signal handler (or a dedicated reload thread) starts freeing the old task list from memory and loading the new one *while* the main loop is still trying to read that exact same list, the program will crash with a Segmentation Fault (reading freed memory).

**How you solved this (Mutexes):**
You used a **POSIX Mutex** (`pthread_mutex_t`), which is essentially a lock.
1. Before the main loop starts scanning the task list, it "locks" the mutex.
2. If a reload signal comes in, the reload function also tries to "lock" the same mutex.
3. Because the main loop already has the lock, the reload function has to wait.
4. Once the main loop finishes scanning the current second, it "unlocks" the mutex.
5. The reload function immediately grabs the lock, safely swaps out the old task list for the new one, and then unlocks it.

This guarantees that the task list is never modified while it is being read.

### Summary Checklist for the Interview
If they ask you to explain the architecture, touch on these key pillars:
*   **The Main Loop:** `sleep(1)` -> check time -> match cron syntax.
*   **Concurrency:** `fork()` and `exec()` to run tasks in isolated parallel processes without blocking the scheduler.
*   **Resource Management:** Trapping `SIGCHLD` and using `waitpid(..., WNOHANG)` to reap zombies asynchronously.
*   **Thread Safety:** Using a `pthread_mutex` to protect the global task array during dynamic `SIGHUP` config reloads.
